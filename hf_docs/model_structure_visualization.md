# 让 HF 模型结构可读：源码、追踪与分层数据流图的组合方案

记录日期：2026-10-11。本文是工程方案与工具选择，不是已完成的自动模型解析器。示例根据 Qwen3 官方配置与本地源码核对，没有运行模型权重或验证数值。

当前执行依据是 [项目计划 v3](model_structure_plan_v3.md)：本期静态提取特征代表，保留条件、状态、实例绑定与源码证据，核验后生成离线阅读页和同源表格。Qwen3-0.6B 是迁移回归案例。v1/v2 与审查记录已归档；本文保留通用方法及远期工具评估，工程范围与命令以 v3 为准。

## 1. 推荐路线

**当前主线：源码 + 配置 → 已审查适配规则 → 带条件/状态的语义图 → 核验 → 离线阅读页与表格。** 远期可用 FX/运行追踪补充连接、shape 与执行证据，ONNX 作为底层核对视图；这些能力不作为 v3 首版前置。

你的两个入口都应保留，但它们可以汇入同一份可读表示：

```text
入口 A：模型配置 + checkpoint → 原始可执行模型
入口 B：配置 + 对应 HF 源码 → 不加载训练权重的模型/单层
                         ↓
模块路径 + 函数操作 + 张量生产/消费 + 状态读写 + 来源位置
                         ↓
保留来源的语义归组与形状说明
                         ↓
整体概览 → 单层 → Attention/MLP → 底层操作
```

对于原生支持的同一模型，这两个入口常常最终使用同一份 Transformers 实现，主要差别是是否加载真实 checkpoint。第二种方式不要手工把每个参数代入 Python；尽量让对应配置类与模型构造器完成配置解释，再分析该对象和代码。

这里的“可读表示”不是重写模型数学计算，而是给已有图增加层级、含义、配置和源码证据。

## 2. 阅读界面应该有四层

### 第一层：整体模型

显示输入、Embedding、层组、最终归一化和任务输出。重复层可折叠，但只有结构相同的层才归组；滑动注意力/全局注意力、MoE/稠密层等差异需要分别显示。概览还要能看见跨层连接和共享组件。

### 第二层：一层的连接

保留 RMSNorm、Attention、Residual Add、MLP 及旁路。必须体现张量在哪里分支、在哪里汇合，不能把模块列表按注册顺序串成直线。

### 第三层：Attention 或 MLP 内部

Attention 显示 Q/K/V 投影、模型特定归一化、RoPE、Cache Update、注意力计算和输出投影；MLP 显示门控投影、激活、逐元素乘法与输出投影。节点旁显示参数与形状，点击可看源码。

**KV Cache 应作为跨调用的状态输入、更新和输出展示，而不是画在 Q→K→Attention 的普通串联路径上。** 一般是 Q 读取查询、K/V 参与缓存更新，注意力同时消费 Q 与可用的 K/V。具体关系以目标源码为准。

### 第四层：需要时展开底层操作

点击 RMSNorm 才展开平方、均值、epsilon、rsqrt、乘法和类型转换；点击布局边才展开 reshape、transpose 等；点击 Attention 才展开或跳到相关 ATen/ONNX 操作。

这样既有直观视图，又可以追问某个节点究竟对应哪段实现。

## 3. 不要直接删除 reshape、transpose 等操作

这些操作可以在默认视图中折叠为边注释，例如：

```text
Q 投影输出 [B,T,Hq×D]
  ── 按头分组与布局转换 ──→ [B,Hq,T,D]
```

但转置的轴、softmax 的轴、RoPE 的位置、切分边界和 GQA 的头映射会影响计算含义。折叠是表现方式，不是宣称它们数学上没有作用。

归组后的节点要保存子图、输入输出端口、来源位置及折叠操作。需要比较 ONNX 时，再打开原始子图。

## 4. 现有工具如何搭配

### 4.1 快速评估：torchview

torchview 可以显示模块、函数操作、输入输出形状，并提供层级深度、嵌套展示与内部张量隐藏等选项，也支持 meta tensor。[项目官方文档](https://github.com/mert-kurttutan/torchview)。

适合先试一个单层/单个 Attention：确认自动生成的连接与折叠粒度是否接近目标。它不保证自动理解所有模型语义，也需要检查具体版本与目标 HF 模型的兼容性。自定义 cache、函数调用和动态分支仍可能要做适配。

### 4.2 实际执行路径与来源：TorchLens

TorchLens 官方资料描述了运行操作的数据依赖、模块归属、形状、代码位置、层级图和重放验证能力。[官方仓库](https://github.com/johnmarktaylor91/torchlens)。

适合在有可运行的小模型/单层时获取更多证据；只记录需要的元信息，避免保存全模型的大量激活。一次输入得到的是那次执行的路径，不等于枚举所有分支。它与 FX/export 是不同采集方案，不能假定可以直接对已经导出的图再次进行同样的 Python 操作捕获。

### 4.3 可控的语义提取：PyTorch FX

自定义 FX tracer 可将 RMSNorm、Linear 或某一级语义模块作为叶子节点，保留 `call_module`，同时记录外部残差、乘法和其他连接。不同展开层级可以采用不同叶子策略。[PyTorch FX 官方文档](https://docs.pytorch.org/docs/2.14/fx.html)。

这适合建设自己的提取层，但不应承诺通吃所有 HF 模型：控制流、Cache 对象、动态 shape 和自定义算子可能阻碍符号追踪。应为目标模型提供明确的 wrapper/adapter，并记录专门化的参数与采样输入。

本地当前 Transformers 源码中未找到旧教程常用的 `utils/fx.py`；不要直接照搬旧版本 HF symbolic_trace 示例，优先核对本地版本并使用适配后的 PyTorch 路径。

### 4.4 层级浏览器：Google Model Explorer

Model Explorer 提供展开/折叠、输入输出高亮、元数据和层级模型浏览，并支持 PyTorch Exported Program 及扩展适配器。[官方仓库](https://github.com/google-ai-edge/model-explorer)。

它的适配器通过 `namespace` 构建层级，通过节点端口建立边，适合作为可读图的展示层。[官方适配器开发指南](https://github.com/google-ai-edge/model-explorer/wiki/6.-Develop-Adapter-Extension)。

但浏览器不会替你判断哪几个运算属于 RMSNorm 或 SwiGLU。直接输入原始低层图仍可能很复杂，需要先由自己的规则和来源信息整理，再提供分层数据。

### 4.5 torch.export 与 ONNX：用于核对底层路径

`torch.export` 提供 ATen 等操作的计算图，包含形状、图签名和相关约束等信息；它仍偏向编译表示，不会天然解决语义拆碎的问题。缺少 fake/meta kernel 和控制流限制也可能使采集失败。[PyTorch 官方 export 文档](https://docs.pytorch.org/docs/2.14/user_guide/torch_compiler/export.html)。

建议将 export/ONNX 作为详细实现证据，与语义节点关联，而非直接当作默认阅读页。

**远期候选组合：torchview 做小范围评估，FX/运行追踪补充采集，Model Explorer 可作替代浏览后端；TorchLens 提供运行证据，ONNX/export 用于详细核对。** 需要对目标版本实测。本期 v3 使用标准库静态适配与自包含 HTML，以上不是当前工程依赖或已验证的安装组合。

## 5. 工程中真正需要补齐的部分

### 5.1 固定分析对象和场景

记录模型 config revision、软件 commit、具体模型类、任务、dtype、attention backend、cache 类型与输入形状。官网权重、自带参考代码和 Transformers 原生实现可能不同，要明确每份图表示哪一个。

把训练与推理、prefill 与 decode、cache 有无、不同注意力 backend 分开。对 DynamicCache 的简单示例，prefill 可令历史长度 P=0、当前长度 T=4；decode 可令 P=4、T=1。这只是两种样例，不表示所有 prefill 都没有历史缓存。

### 5.2 建立中间图数据

节点至少保存：语义类型、实例/调用 ID、模块路径、父层级、输入输出端口、来源文件与位置、配置属性、证据类型。

边至少保存：生产者端口、消费者端口、tensor ID/版本、shape、轴含义、dtype、布局变换与数据/状态/控制类别。

shape 默认带轴符号和数值，图旁给出全名；端口细节记录中文含义和数值来源。例如 `hidden_states [B=1,T=1,N_hc=4,H=4096]` 中 B 是 batch_size、T 是本次 seq_len、N_hc 来自 hc_mult、H 来自 hidden_size。不能只输出裸数字；hidden_states 是张量名称，不是轴名称。详细规则见项目计划第 2 节。

同一个模块被多次调用要有独立调用 ID；缓存原地更新、tensor view 与别名不能只靠 Python 对象地址区分。

### 5.3 连接必须有依据

`named_modules()` 只能得到模块树；forward hooks 的调用时间只能说明执行先后。**两者都不能单独证明完整的数据流。**

应使用 FX 图边或执行中的生产者—消费者信息，再配合模块作用域和函数操作捕获。`Cache.update`、RoPE、残差和函数式乘法并不都属于 `nn.Module`，不能只靠 module hooks。

### 5.4 用来源归组，而不是只靠外观猜算子

优先依据已知模型类、模块路径、源码位置和调用范围归组。缺少这些信息时，才尝试匹配低层子图，匹配后也要检查 epsilon、归一化轴、广播和 dtype。

RMSNorm 应保留其 dtype 转换与公式细节；SwiGLU 应保留 gate/up 两个分支与乘法。不能看到类似 `pow + mean + mul` 就自动标成已确认的 RMSNorm。

### 5.5 区分不同验证等级

- **源码核对**：根据源码与配置识别结构，尚未执行。
- **形状追踪**：meta/fake 等方式检查连接和形状，不含真实数值证据。
- **运行追踪**：目标模型某组输入实际执行过的路径。
- **数值验证**：变换/重放结果与参考结果在规定误差内一致。

没有实际执行过的分支应标记为“未覆盖”，不能用 AI 推测的连接补成“已验证”。

## 6. 没有完整权重时能做到哪些

多数常规稠密模型的静态结构可以用配置和对应程序构造出来，不必为了观察结构下载全部训练权重。meta device 只保存参数与张量元数据，可降低参数存储需求；但仍有 Python 对象和图数据开销，且依赖可用的 meta/fake 实现。[PyTorch meta 官方说明](https://docs.pytorch.org/docs/2.14/meta.html)。

失败时可使用单层、保留结构特征的小规模随机模型或源码核对作为降级方案。缩小后的模型必须明确标记；不能认为改变隐藏维度、头数或专家数后就是原模型的完整验证。

配置不足以决定 MoE 的实际路由、数据相关分支或最终数值，量化与自定义算子也可能有额外限制。本项目暂缺权重，适合先做源码与配置驱动的结构图，再补运行证据。

## 7. Skill 应承担什么职责

建议把成熟流程固化成项目的“模型结构阅读” skill，**skill 管流程和呈现规范，编码工程负责提取与验证**。这是建议新建的 skill，目前尚未创建。

skill 的固定流程可以是：

1. 识别模型与软件版本，读取配置、入口及依赖。
2. 选择已有模型 adapter，明确分析场景。
3. 调用工程脚本采集模块、操作、形状、缓存和来源证据。
4. 应用经过检查的语义归组，保留未覆盖和失败信息。
5. 输出可浏览的图及简洁中文阅读说明。
6. 核对重点连接、shape 与缓存；按能力标记验证等级。

本会话的 `visualize` 技能适合展示概念和交互阅读示例；它本身不是模型图提取器。`skill-creator` 适合在流程稳定后将规则和工具入口整理成可复用 skill。仅让 AI 读源码画图不宜作为唯一正确性依据，尤其是状态和动态分支。

## 8. 适合当前项目的最小建设范围

以当前 **DeepSeek-V4-Flash-0731** 为主案例，先建立一个 CSA·TopK 代表闭环，再补主干变体与 DSpark；完整节点和验收见 [v3 第 6 节](model_structure_plan_v3.md#6-开发阶段与责任)。Qwen3-0.6B 用于对照普通残差、独立 Q/K/V 和迁移复用。

当前工程区分规则声明、静态提取、独立核验、渲染和导出，统一使用 `structure_reader/`；阅读页为自包含 HTML。脚本、库代码、测试、分析设置、文档与正式产物按 v3 的目录规范分别落位。

下列为通用阅读目标；v3 首版的展开范围和核验以当前计划为准，RMSNorm 底层算术/ATen 等能力留作后续：

- 默认只展示语义节点，能展开 Attention、MLP、RMSNorm 与布局操作。
- 连接和节点可追到源码，重要端口显示 shape 与轴含义。
- Q/K/V 为并行分支，RoPE、归一化和 Cache Update 的顺序准确。
- 残差旁路、掩码及跨调用缓存状态没有丢失。
- prefill/decode 有独立场景标签，未追踪部分有清楚标记。
- 重复层只按经核对的同构结构折叠。

以上 Q/K/V 和残差验收适用于 Qwen3 对照案例。DeepSeek 使用共享 KV 和 mHC，必须使用它自己的结构规则；不能强行套用该示例。再用不同稠密/MoE 模型检验通用部分，多模态等未测机制另行扩展。

## 9. Qwen3 阅读示例的依据

官网 Qwen3-0.6B 配置提供 hidden_size=1024、16 个 Q 头、8 个 KV 头、head_dim=128、MLP 中间维度 3072。因此不能简单假设 head_dim=hidden_size/头数。[官网配置](https://huggingface.co/Qwen/Qwen3-0.6B/blob/main/config.json)。

本地 `Qwen3Attention.forward` 中，Q/K 各自投影后按头分组并归一化，再应用 RoPE；K/V 随后参与缓存更新，注意力消费 Q 与更新后的 K/V，最后经过输出投影。`Qwen3MLP.forward` 有 gate/up 两个分支。[本地源码](../hflib/transformers/src/transformers/models/qwen3/modeling_qwen3.py)。

会话中的可切换示例依据这些配置与源码构建，是**源码核对的展示样例**，不是自动追踪器输出，也没有运行验证。布局转换折叠在形状/说明里，底层归一化可单独展开。
